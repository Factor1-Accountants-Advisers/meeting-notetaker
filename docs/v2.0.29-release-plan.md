## 3. Cut sequence

Run in order. Steps 3.2 and 3.4 have been classifier-blocked before; run
them yourself with a `!` prefix if they are.

**3.1 — Merge and bump**

```
git checkout main
git merge --no-ff codex/sharepoint-permission-hardening
npm version 2.0.29 --no-git-tag-version
git commit -am "chore: bump version to 2.0.29"
git push origin main
```

The bump is deliberately *not* pre-applied: the repo's pattern
(`6693796`, PR #7) is to bump on `main` after the feature merge, and a
version bump sitting on a feature branch invites a stale tag.

**3.2 — PATCH the signing federated credential (before tagging)**

The tenant matches the FIC subject **literally** — the `refs/tags/v*`
wildcard does not work here. Signing fails if this is skipped.

Save this as `tmp/fic-v2.0.29.json` in the repo root (`tmp/` is
gitignored). A repo-relative path matters: `az` is a Windows binary and
cannot resolve a Git Bash `/tmp/...` path.

```json
{
  "name": "github-release-v2-0-8",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:Factor1-Accountants-Advisers/meeting-notetaker:ref:refs/tags/v2.0.29",
  "audiences": ["api://AzureADTokenExchange"],
  "description": "IN-81: signs release builds via Azure Artifact Signing (as-factor1)"
}
```

Then, from the repo root (works in both PowerShell and Git Bash):

```
az ad app federated-credential update --id 5e1334af-b687-4636-880f-79f97879b69e --federated-credential-id f2849212-1ed8-4d7b-9279-ed4b7cdf98ce --parameters tmp/fic-v2.0.29.json
```

`--parameters` takes a JSON file path or an inline JSON string. The file
form avoids the quoting differences between the two shells.

Confirm before tagging:

```
az ad app federated-credential list --id 5e1334af-b687-4636-880f-79f97879b69e \
  --query "[].{name:name,subject:subject}" -o table
```

**3.3 — Tag and push**

```
git tag v2.0.29
git push origin v2.0.29
```

**3.4 — Verify the release**

- CI run green, including the signing and credentials assertions
- Feed: `curl -s https://stf1nt.blob.core.windows.net/updates/latest.yml`
  → `version: 2.0.29`, sha512 matches the installer
- `Get-AuthenticodeSignature` on the setup exe → Valid, subject
  `CN=factor1.com.au`, Microsoft timestamp present
- Blockmap present alongside the installer
- Installer size ~162 MB (a jump to ~213 MB means the native audio helper
  crept back in — that was the v2.0.17 regression)

## 4. Post-release

**4.1 — Intune re-wrap (hand to DV). Not optional.**

The OpenAI key is baked into the packaged `backend.env` at build time, so a
stale Intune package installs the **old** key. On 6 Aug IT was still
deploying v2.0.12, eight releases behind the 4 Aug rotation, and every fresh
install failed with `pyannoteAI HTTP 401` — read as a product defect.

- Re-wrap the signed v2.0.29 installer
- Deploy in **user context** (installs to `%LOCALAPPDATA%\Programs\`)
- Detection rule **"this version or greater"**, never an exact match — an
  exact match stops matching the moment a machine auto-updates, after which
  Intune reinstalls the older build over the newer one

**4.2 — Fleet**

Watch for machines that silently ignore the feed because the MS Enterprise
Identity Verification Root CA 2020 never landed (Gabby-class; Jose's Legion
was still blocked as of early Aug). They need a manual over-the-top install.

**4.3 — Revoke the old OpenAI key. Last step, not before.**

Preconditions, all of them:

- [ ] New key live ~48h (Joseph's rule)
- [ ] Fleet on v2.0.29
- [ ] **Vercel hosted env vars updated** for `policy-chatbot-v2` and
      `factor1vibe` — both call `requireEnv("OPENAI_API_KEY")` and will hard
      fail. The local `.env.local` files are already updated; the hosted ones
      are not. Vercel CLI is not installed on this machine.

Then revoke in the OpenAI dashboard and smoke: one meeting summary
end-to-end, one chatbot query.

## 5. Release notes (v2.0.29 as shipped)

**End users** — **transcripts and summaries now go to the person who
recorded the meeting only.** Invitees no longer receive the email, and no
longer get SharePoint access to the files. This is temporary while the firm
gets used to the tool; the organiser can forward as they see fit. No other
visible change.

**IT / DV** — signed installer, re-wrap for Intune (§4.1). Contains a
rotated OpenAI credential, so a stale package installs a key that will stop
working once the old one is revoked. pyannote credential unchanged.

**Projects** — the organiser-only mode was requested by David F on 18 Aug
after an unrelated in-person conversation was auto-recorded and sent to a
scheduled meeting's invitees. Restoring invitee delivery later is a repo
variable (`MN_DELIVERY_RECIPIENTS=attendees`) plus a release. The
"start recording only when the user actually joins" work is the durable
fix and is the next feature.

**Not in this release:** the SharePoint transcript permission hardening
(IN-91/IN-398) — see the deferral note at the top; it ships as v2.0.30.

## 6. Known residuals

- **Legacy transcripts remain broadly accessible.** This release protects
  future uploads only. Deferred by Joseph 18 Aug; still the live exposure.
- **Allowlist strictness.** The privacy gate now blocks *any* unexpected
  principal, read-only included. If a user manually shares their own
  transcripts folder, their uploads stop until it is removed. Relaxing this
  to write-only is a two-line change in
  `_verify_owner_folder_permissions`.
- **CI checks key presence, not validity.** `release.yml` refuses to build
  on an empty secret but never probes it, so a typo'd or revoked key
  produces a green, signed build that fails on every machine at summary
  time. Not addressed here; worth a liveness probe.
